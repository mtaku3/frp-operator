frp-operator detects configuration drift using a two-level hash scheme. When either the `ExitPool` template or the referenced `ProviderClass` changes, claims created from the old configuration are detected as "drifted" and replaced.

## Why two levels?

The pool template and the provider config evolve independently:

- A user may update the `frps.version` in the pool template (pool-level change)
- A user may rotate the DigitalOcean API token in the `DigitalOceanProviderClass` (provider-level change)

Tracking them as separate hashes means each change type can be independently detected and attributed. Both hashes live on the same annotation set, so the drift check is a single annotation comparison.

## Pool hash (`frp.operator.io/pool-hash`)

The pool hash is a SHA-256 over `ExitPool.Spec.Template.Spec` (the template content). It is stamped on:

- `ExitPool.metadata.annotations["frp.operator.io/pool-hash"]` — the current value
- `ExitClaim.metadata.annotations["frp.operator.io/pool-hash"]` — the value at claim creation time

When a claim is created from a pool, the claim's pool-hash annotation is set to the pool's current pool-hash. If the pool template is later changed, the pool's annotation updates and the claim's annotation becomes stale — the values differ.

## ProviderClass hash (`frp.operator.io/providerclass-hash`)

The providerclass hash is a SHA-256 over the `Spec` field of the referenced `ProviderClass` object (computed via reflection). It follows the same stamping pattern:

- Pool: `ExitPool.metadata.annotations["frp.operator.io/providerclass-hash"]`
- Claim: `ExitClaim.metadata.annotations["frp.operator.io/providerclass-hash"]`

The providerclass hash controller watches all `ProviderClass` objects. When a ProviderClass spec changes, the controller recomputes the hash, stamps it on the ProviderClass, propagates it to all referencing ExitPools, and from there to each ExitClaim via the drift detection path.

## Hash computation

Both hashes use the same scheme: SHA-256 over the JSON-marshaled spec, truncated to the leading 16 hex characters (64 bits). This matches the scheme used by Karpenter for NodeClass hashes.

```go
sum := sha256.Sum256(raw)
hash := hex.EncodeToString(sum[:])[:16]
```

## Drift check

The `Drift` disruption method compares annotations:

```go
// hashesDiffer returns true if both annotations are present AND differ.
// Missing on either side → "not drifted yet" (safe by design)
claimHash := claim.Annotations["frp.operator.io/pool-hash"]
poolHash  := pool.Annotations["frp.operator.io/pool-hash"]
if claimHash != "" && poolHash != "" && claimHash != poolHash {
    // claim is drifted
}
```

The "missing = not drifted" convention means:

- Claims created before the hash controller first ran are not spuriously evicted.
- A pool that has never been hashed will not trigger drift on any of its claims.

## What triggers a drift?

| Change | Which hash changes |
|---|---|
| `spec.template.spec.frps.version` updated | pool-hash |
| `spec.template.spec.requirements` changed | pool-hash |
| `spec.template.spec.frps.allowPorts` changed | pool-hash |
| `DigitalOceanProviderClass.spec.imageSelectorTerms` changed | providerclass-hash |
| `DigitalOceanProviderClass.spec.apiTokenSecretRef` changed | providerclass-hash |
| `LocalDockerProviderClass.spec.network` changed | providerclass-hash |
| `spec.disruption.*` changed | **no hash change** — disruption policy is not part of the template hash |
| `spec.limits.*` changed | **no hash change** |

<Aside type="tip">
Disruption policy and limit changes take effect immediately without replacing existing claims. Only changes inside `spec.template.spec` trigger pool-hash drift.
</Aside>

## Drift replacement flow

1. User changes a field covered by the pool-hash or providerclass-hash.
2. The hash controller recomputes and stamps the new hash on the pool.
3. At the next disruption tick, the `Drift` method compares claim annotations to pool annotations.
4. Claims with stale hashes are selected as drift candidates.
5. The controller creates replacement claims (with the new hash), then deletes the old claims.
6. Tunnels rebind to the replacement claims.

The replacement is gated by disruption budgets, so a large pool does not have all its claims replaced simultaneously.

<Aside type="caution">
Changing `spec.template.spec.frps.version` triggers drift for **all** claims in the pool. In a pool with 10 exits, this means 10 replacements over time. Use a disruption budget (`nodes: "2"`) to control the rollout rate.
</Aside>
