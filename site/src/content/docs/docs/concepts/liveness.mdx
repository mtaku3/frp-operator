After an `ExitClaim` reaches `Ready=True`, the lifecycle controller continuously probes the frps daemon's admin HTTP API. A sustained failure causes the claim to be cordoned (new Tunnels cannot bind to it) and eventually replaced.

This mirrors the Karpenter NodeHealth controller pattern: periodic probe → threshold → cordon → replace.

## Two-phase probing

### Phase 1: Pre-Ready (registration timeout)

While a claim has `Launched=True` but not yet `Registered=True`, the controller waits up to `RegistrationTTL` (default 15 minutes) for the frps admin API to respond. If the TTL expires without a successful admin API response:

- `Disrupted=True` is set with reason `RegistrationTimeout`
- The claim is deleted (no replacement — the scheduler will create a fresh one when the next Tunnel event fires)

### Phase 2: Post-Ready (continuous probe)

Once the claim has `Ready=True`, the controller probes `http://<publicIP>:<adminPort>/api/serverinfo` every `ProbeInterval` (default 30 seconds).

**On success:** If a failure counter annotation exists, it is cleared.

**On failure:** The failure count is incremented in the annotation `frp.operator.io/liveness-failures`. After `FailureThreshold` (default 3) consecutive failures:

1. `Ready=False` is set with reason `AdminAPIUnreachable`
2. `Disrupted=True` is set with reason `AdminAPIUnreachable`

The disruption controller then picks up the claim and triggers a replacement.

## Constants

| Parameter | Default | Configurable via |
|---|---|---|
| `RegistrationTTL` | 15 minutes | `--registration-ttl` flag |
| `ProbeInterval` | 30 seconds | (internal constant, not exposed as a flag) |
| `FailureThreshold` | 3 consecutive failures | (internal constant, not exposed as a flag) |

## Cordon-via-condition

When `Disrupted=True` is set on a claim, the scheduler stops binding new Tunnels to it. This is the "cordon" equivalent — Tunnels that arrive while the replacement is being provisioned are not placed on the doomed claim. They either bin-pack onto other healthy claims or wait for the replacement to become Ready.

This prevents a failing exit from accumulating new Tunnels just before it is deleted, which would cause double disruption (new Tunnel bound → exit deleted → Tunnel re-schedules).

## How Tunnels rebind

When the failed claim is replaced:

1. The disruption controller creates a new ExitClaim (replacement) from the pool template.
2. The lifecycle controller brings the replacement to `Ready`.
3. The provisioner's next batch cycle detects Tunnels whose `AssignedExit` no longer exists and re-schedules them onto the new (or any other Ready) claim.

Traffic is interrupted for the duration of the replacement VM boot + frps registration, typically 60–120 seconds for a DigitalOcean Droplet.

## Failure annotation

You can observe the current failure count:

```bash
kubectl get exitclaim <name> -o jsonpath='{.metadata.annotations.frp\.operator\.io/liveness-failures}'
```

A value of `0` (or absent) means the last probe succeeded. A value of `1` or `2` means probes are failing but the threshold has not been reached yet.

## Trade-offs

| Behavior | Value | Consideration |
|---|---|---|
| Short `ProbeInterval` | Faster detection | More admin API calls; noisier in logs |
| Low `FailureThreshold` | Faster replacement | May trigger on transient network hiccups |
| High `FailureThreshold` | More tolerant of noise | Longer window where traffic to a broken exit is accepted |

<Aside type="caution">
The probe contacts the frps admin API using the claim's `status.publicIP`, not via the Kubernetes Service. If the VM is up but the frps process has crashed, the probe will fail even though the VM responds to SSH. This is the desired behavior — the operator cares whether frps is alive, not whether the VM itself is reachable.
</Aside>
