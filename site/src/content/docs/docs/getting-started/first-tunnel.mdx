Expose a Kubernetes Service to the internet using the local Docker provider. This is the fastest way to see frp-operator in action on a kind cluster — the frps server runs as a Docker container on your machine rather than a cloud VM.

## Prerequisites

- frp-operator installed (see [Install on kind](./install-kind))
- Docker accessible from the kind cluster nodes (the default on kind)
- A Service you want to expose, or you can use the example nginx below

<Aside type="caution">
`LocalDockerProviderClass` is for development only. It runs frps in a Docker container on the host and is not suitable for production traffic.
</Aside>

## Steps

<Steps>

1. **Create a test Service**

   If you don't have a Service to expose, create a simple nginx one:

   ```bash
   kubectl create deployment nginx --image=nginx:alpine
   kubectl expose deployment nginx --port=80
   ```

2. **Apply a LocalDockerProviderClass**

   The `LocalDockerProviderClass` tells the operator how to launch frps containers. The `network: kind` field attaches containers to the kind Docker network so the operator pod can reach them.

   ```yaml
   # local-docker-provider.yaml
   apiVersion: frp.operator.io/v1alpha1
   kind: LocalDockerProviderClass
   metadata:
     name: local
   spec:
     network: kind
     configHostMountPath: /tmp/frp-operator-shared
     imagePullPolicy: IfNotPresent
     defaultImage: "fatedier/frps:%s"
   ```

   ```bash
   kubectl apply -f local-docker-provider.yaml
   ```

3. **Apply an ExitPool**

   An `ExitPool` is the pool of frps exits. It references the `LocalDockerProviderClass` via `providerClassRef` and defines which ports the frps daemon may hand out to tunnels.

   ```yaml
   # exit-pool.yaml
   apiVersion: frp.operator.io/v1alpha1
   kind: ExitPool
   metadata:
     name: local-pool
   spec:
     template:
       spec:
         providerClassRef:
           group: frp.operator.io
           kind: LocalDockerProviderClass
           name: local
         frps:
           version: "v0.61.1"
           bindPort: 7000
           adminPort: 7400
           allowPorts:
             - "1024-65535"
           auth:
             method: token
         requirements:
           - key: node.kubernetes.io/instance-type
             operator: In
             values: ["local"]
     disruption:
       consolidationPolicy: WhenEmpty
       consolidateAfter: 5m
   ```

   ```bash
   kubectl apply -f exit-pool.yaml
   ```

4. **Apply a Tunnel**

   A `Tunnel` references the Service you want to expose and declares the port mapping. `publicPort: 0` means auto-assign from the pool's `allowPorts` range.

   ```yaml
   # tunnel.yaml
   apiVersion: frp.operator.io/v1alpha1
   kind: Tunnel
   metadata:
     name: nginx-tunnel
     namespace: default
   spec:
     ports:
       - name: http
         servicePort: 80
         publicPort: 0
         protocol: TCP
   ```

   ```bash
   kubectl apply -f tunnel.yaml
   ```

5. **Watch the Tunnel reach Ready**

   ```bash
   kubectl get tunnel nginx-tunnel -w
   ```

   The Phase column progresses through:

   ```
   NAME           PHASE         EXIT   IP   AGE
   nginx-tunnel   Allocating         <none>   5s
   nginx-tunnel   Provisioning       <none>   10s
   nginx-tunnel   Ready        local-pool-abc123   203.0.113.5   45s
   ```

   Check the assigned public port:

   ```bash
   kubectl get tunnel nginx-tunnel -o jsonpath='{.status.assignedPorts}'
   ```

6. **Inspect what the operator created**

   An `ExitClaim` was provisioned automatically:

   ```bash
   kubectl get exitclaim
   ```

   ```
   NAME               POOL         PROVIDER                READY   PUBLICIP       AGE
   local-pool-abc123  local-pool   LocalDockerProviderClass True    203.0.113.5    60s
   ```

   Describe the claim to see its conditions:

   ```bash
   kubectl describe exitclaim local-pool-abc123
   ```

   The conditions progress: `Launched=True` → `Registered=True` → `Initialized=True` → `Ready=True`.

</Steps>

## What the operator did

1. The `Tunnel` creation triggered the provisioner's batch window (default 1s idle / 10s max).
2. The scheduler found no existing Ready `ExitClaim` with capacity, so it created one from the `ExitPool` template.
3. The lifecycle controller launched a Docker container running `fatedier/frps:v0.61.1`, wrote an `frps.toml` config, and waited for the frps admin API to respond.
4. Once the admin API responded, the claim moved to `Ready=True`.
5. The provisioner promoted the `Tunnel` from `Provisioning` to `Ready` and populated `status.assignedIP` and `status.assignedPorts`.

## Cleanup

```bash
kubectl delete tunnel nginx-tunnel
kubectl delete exitpool local-pool
kubectl delete localdockerproviderclass local
kubectl delete deployment nginx
kubectl delete service nginx
```

The operator drains the tunnel from the ExitClaim, and because the pool's `consolidationPolicy` is `WhenEmpty`, the claim (and its Docker container) is deleted after the `consolidateAfter` window expires.
