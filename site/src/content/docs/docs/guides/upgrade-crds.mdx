**Goal:** Safely upgrade the frp-operator CRDs when a new version ships schema changes, without disrupting running tunnels.

## Why a split-chart layout?

Helm has a known limitation: it does not upgrade CRDs that already exist when running `helm upgrade`. CRDs bundled in a chart's `crds/` directory are installed on first `helm install` but silently skipped on every subsequent `helm upgrade`.

frp-operator uses a **split-chart layout** to work around this:

- `frp-operator-crd` — contains only CRDs, installed as regular templated resources (not in `crds/`). This means Helm's full lifecycle applies: install, upgrade, rollback.
- `frp-operator` — contains the controller Deployment and supporting resources. It never touches CRDs.

This pattern is identical to the approach used by cert-manager, Karpenter, and other projects with complex CRD lifecycles.

## Upgrade procedure

<Steps>

1. **Upgrade the CRD chart first**

   Always upgrade CRDs before upgrading the operator. The new operator version may depend on new or modified fields that must exist in the API server before the controller starts.

   ```bash
   helm upgrade frp-operator-crd \
     oci://ghcr.io/mtaku3/charts/frp-operator-crd \
     --version <NEW_VERSION> \
     --namespace frp-operator-system \
     --wait
   ```

   Verify the CRDs were updated:

   ```bash
   kubectl get crd exitpools.frp.operator.io -o jsonpath='{.metadata.annotations.meta\.helm\.sh/release-name}'
   ```

2. **Upgrade the operator chart**

   After CRDs are in place, upgrade the controller:

   ```bash
   helm upgrade frp-operator \
     oci://ghcr.io/mtaku3/charts/frp-operator \
     --version <NEW_VERSION> \
     --namespace frp-operator-system \
     --wait
   ```

3. **Verify the operator is healthy**

   ```bash
   kubectl -n frp-operator-system get pods
   kubectl -n frp-operator-system logs -l app.kubernetes.io/name=frp-operator --tail=50
   ```

   The operator performs a reconciliation pass on startup. Existing `ExitClaims` and `Tunnels` will be re-reconciled but should not be disrupted unless the pool template hash changed (see [Hash drift](../concepts/hash-drift)).

</Steps>

## Rollback

If the new operator version is unhealthy, roll back the operator chart first:

```bash
helm rollback frp-operator --namespace frp-operator-system
```

Then, if necessary, roll back the CRD chart:

```bash
helm rollback frp-operator-crd --namespace frp-operator-system
```

<Aside type="caution">
Rolling back CRDs is safe only if no CRs using the new schema fields were created between the CRD upgrade and the rollback. Fields added in the new version that are now absent in the old schema will be silently dropped by the API server.
</Aside>

## Checking for breaking schema changes

Before upgrading, review the release notes for the target version. Schema changes that affect existing CRs are marked as breaking. If a field is removed or renamed, you must migrate existing resources before the CRD upgrade:

```bash
# Dump all ExitPools to YAML before upgrading
kubectl get exitpool -o yaml > exitpools-backup.yaml

# Dump all Tunnels
kubectl get tunnel -A -o yaml > tunnels-backup.yaml
```

## Why the order matters

If you upgrade the operator chart before the CRD chart and the new operator version references fields that don't exist in the old CRD schema, the operator will fail to start with a schema validation error or produce garbage output when it tries to patch a resource with an unknown field.

The safe order is always: **CRD chart first, operator chart second**.
