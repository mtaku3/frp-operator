In some cases there may be a need to do a full uninstall and re-install of frp-operator. An example could be when a very old frp-operator version needs to be brought up to date and it isn't feasible to upgrade one minor version at a time, which is our default recommended upgrade strategy.

If frp-operator `CustomResourceDefinition`s are also uninstalled, this will mean loss of associated frp-operator custom resources such as `Tunnel`s and `ExitPool`s. The main concern associated with this is application downtime and unnecessary tunnel disruption. The `frp-operator-crd` chart annotates all CRDs with `helm.sh/resource-policy: keep`, which means that `helm uninstall` will **not** remove the CRD objects or any custom resources stored inside them. Your data is preserved by default — only a manual `kubectl delete crd` step will remove it.

If the `Tunnel`s and `ExitPool`s get deleted and re-applied, but the underlying exit node allocations remain in your infrastructure, the newly applied resources should be able to reconcile back to a healthy state without unnecessary re-provisioning, depending on your provider configuration.

When uninstalling and re-installing in order to upgrade, you should still read through the release notes for each skipped version.

Some things to look out for when considering uninstalling and re-installing frp-operator _including the CRDs_:

- Are there currently any tunnel connections or exit node provisioning operations in progress? If so, with the custom resources deleted, the progress will be lost. This could potentially cause duplicated provisioning.
- Is there a need to convert frp-operator custom resource manifests to a newer API version? Check the [CRD reference](/docs/reference/crds/) for the current API versions.
